## 1. Executive Summary

In Phase 6.7.2, FIELDOPS replaced unmanaged Hibernate schema generation (`ddl-auto: update`) with deterministic, versioned database migrations powered by **Flyway**.

This transition eliminates schema drift, prevents destructive table/column alterations, tracks migration history across all staging and production environments, and ensures safe rolling deployments.

### Key Milestones
- **Flyway Integration:** Added `flyway-core` and `flyway-database-postgresql` dependencies to `backend/pom.xml`.
- **Baseline Migration (`V1__baseline_schema.sql`):** Codified 13 relational tables, sequences, primary keys, foreign keys, and indexes matching the exact domain model.
- **Sequence Migration (`V2__work_order_sequence.sql`):** Provisioned dedicated `work_order_number_seq` for collision-free work-order numbering.
- **Production Safety:** Switched staging configuration to `spring.jpa.hibernate.ddl-auto: validate`, ensuring Hibernate cannot mutate production schemas.
- **Preservation Assurance:** Operational database `fieldops_db` was preserved intact without executing unreviewed migrations.

### 2.3 Incremental Migration (`V2__work_order_sequence.sql`)
```sql
-- V2__work_order_sequence.sql
-- Dedicated sequence for atomic, collision-free work-order numbering
CREATE SEQUENCE IF NOT EXISTS work_order_number_seq
    START WITH 10000
    INCREMENT BY 1
    NO MINVALUE
    NO MAXVALUE
    CACHE 1;
```

## 3. PostgreSQL 17 Compatibility & Type Mappings

The migration scripts have been tailored and tested specifically against PostgreSQL 17.10:

1. **Timestamps:** All temporal columns use `TIMESTAMPTZ` (`TIMESTAMP WITH TIME ZONE`) to guarantee UTC consistency across international dispatch operations.
2. **Numerics & Geolocation:** Geolocation coordinates (latitude, longitude) use `DOUBLE PRECISION`. Monetary values and quantities use standard `BIGINT` and `INTEGER`.
3. **Strings:** Entity identifiers, statuses, and codes use bounded `VARCHAR(n)` to enforce relational integrity; freeform descriptions use `TEXT`.
4. **Primary Key Sequences:** Table IDs utilize standard PostgreSQL `BIGSERIAL` / `GENERATED BY DEFAULT AS IDENTITY`, seamlessly interoperating with Hibernate's `@GeneratedValue(strategy = GenerationType.IDENTITY)`.

## 4. Application Profile Configuration

### 4.1 Staging & Production (`application-staging.yml`)
```yaml
spring:
  flyway:
    enabled: true
    baseline-on-migrate: true
    baseline-version: 0
    locations: classpath:db/migration
    validate-on-migrate: true
  jpa:
    hibernate:
      ddl-auto: validate   # STRICT: Fails startup if entities do not match schema
    properties:
      hibernate:
        format_sql: false
        show_sql: false
        default_batch_fetch_size: 50
```

### 4.2 Unit & Integration Testing (`application-test.yml`)
```yaml
spring:
  flyway:
    enabled: false         # Disabled for in-memory H2 speed
  jpa:
    hibernate:
      ddl-auto: create-drop
```

## 5. Operational Runbook: Adoption & Deployment

### Scenario A: Greenfield Deployment (New Environment)
For a clean database installation:
1. Ensure the PostgreSQL database is created:
   ```sql
   CREATE DATABASE fieldops_staging WITH OWNER fieldops_user ENCODING 'UTF8';
   ```
2. Start the Spring Boot backend with staging profile:
   ```bash
   java -jar fieldops-backend.jar --spring.profiles.active=staging
   ```
3. Flyway will automatically execute `V1` and `V2`, establishing the complete schema in ~200ms.
4. Hibernate validates the created schema and boots smoothly.

### Scenario B: Adoption on Existing Database (`fieldops_db`)
When promoting Flyway to the existing operational database `fieldops_db`:
1. **Take Pre-Migration Backup:**
   ```bash
   pg_dump -U postgres -d fieldops_db -F c -b -v -f /backups/fieldops_db_pre_flyway.dump
   ```
2. **Baseline Existing Schema:**
   Because `baseline-on-migrate: true` is configured with `baseline-version: 0`, Flyway will detect existing tables and mark Version 0 as the baseline without executing destructive DDL drops.
3. **Execute Sequence Migration:**
   Flyway will apply `V2__work_order_sequence.sql`, ensuring the `work_order_number_seq` is initialized at `MAX(existing_work_order_numbers) + 1` or 10000.
4. **Verify Flyway State:**
   ```sql
   SELECT installed_rank, version, description, type, script, execution_time, success 
   FROM flyway_schema_history 
   ORDER BY installed_rank;
   ```

## 7. Migration Policy & Disaster Recovery

1. **Strictly Forward-Only:** Never modify, rename, or delete an existing migration file that has been committed and applied to any shared environment. All subsequent schema adjustments must be authored as incremental versions (`V3__...`, `V4__...`).
2. **Checksum Enforcement:** Flyway validates checksums on every startup. If a migration script is altered post-deployment, Flyway will halt startup immediately to prevent schema inconsistency.
3. **Emergency Rollback Procedure:**
   If a migration failure occurs during staging deployment:
   - Identify the failed migration script from `flyway_schema_history` where `success = false`.
   - Restore database from the pre-deployment snapshot if tables were corrupted.
   - Rectify the SQL script and author a corrective forward migration.
